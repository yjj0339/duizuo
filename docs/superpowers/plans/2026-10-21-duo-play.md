# DUO PLAY Implementation Plan

> **For agentic workers:** Use the documented shared interfaces to implement independent game groups, followed by owner integration and review. Steps use checkbox syntax for tracking.

**Goal:** Deliver 20 complete two-player browser games with a GitHub Pages frontend and a D: local authoritative multiplayer server.

**Architecture:** One Socket.IO room service owns identity, readiness, snapshots, reconnect and tournament state. Independent game engine/renderer groups implement the exact interface in `docs/CONTRACT.md`. The frontend supports a real online server plus an explicitly labelled same-device two-player local mode.

**Tech Stack:** ESM JavaScript, Vite, Node 24, Socket.IO, built-in SQLite, node:test, Playwright.

**Spec:** `docs/制作提示词.md` and `docs/CONTRACT.md`.

## Global Constraints

- Exactly 20 games with the IDs in the contract.
- Everything executed, downloaded or generated stays on D:; never invoke the C: Node installation.
- Preserve all previous project files; only reference their rules.
- Server is authoritative. Private game information is filtered per player.
- No credentials in GitHub or project artifacts.
- Publish GitHub Pages and test actual multiplayer; distinguish tunnel lifetime from permanent hosting.

## Review Focus

- A third tab cannot steal a full room or impersonate an existing token.
- Reconnecting/duplicate actions cannot replay a move or start duplicate games.
- Live snapshots cannot steal IME focus or reset a held pointer/slider.
- Hidden state remains absent from opponent snapshots.
- Mobile safe areas, 320px width and game controls remain usable.

## Task 1: Shared rules and UI groups

Files: the three independent group pairs and CSS listed in CONTRACT.md, plus corresponding tests.
Interfaces: create/action/tick/view and mount/update/destroy exactly as in CONTRACT.md.

- [ ] Write meaningful failing tests for each group's win conditions, rejected moves, timing and hidden state.
- [ ] Run each group suite with the D: Node executable and observe failure before implementing.
- [ ] Implement complete games and touch/keyboard renderers.
- [ ] Run suites to pass and write group action/report documentation.

## Task 2: Room protocol and persistence

Files: `server/rooms.js`, `server/index.js`, `tests/rooms.test.js`, `shared/catalog.js`.
Interfaces: RoomService with create/join/ready/action/leave/reconnect via Socket.IO request acknowledgments; event `snapshot` with personalized `{ room, game, player }`; health GET `/health`.

- [ ] Write failing room tests for capacity, two-player readiness, token auth, invalid/repeated events, rejoin and series.
- [ ] Implement strict input validation, session tokens, action IDs, rates, disconnect grace and server snapshots.
- [ ] Save completed results to SQLite and expose no sensitive paths or tokens publicly.
- [ ] Verify real Socket.IO clients play and reconnect through the actual HTTP server.

## Task 3: Responsive frontend and local practice

Interfaces: import catalog and group renderers; online via Socket.IO with ack errors, local via the same engines.

- [ ] Implement ready room, game shell, results, rematch, game switching and 3/5-round series.
- [ ] Support invite URL including configured HTTPS server, real status/latency, sound preference and local history.

- [ ] Install dependencies into the isolated project with D: cache and temp.

## Design decisions

Cloud white #f6faf9, ink #243d3b, teal #40ae9a, coral #ee827f, lavender #a49bdb. System Chinese sans-serif typography, with large round DUO lettering. Desktop: narrow navigation rail + wide lobby and a persistent room panel. Mobile: compact header, two-column games and bottom-safe room actions. Custom isometric mini-board art for hero and individual game tiles; avoid dependence on remote fonts/images. Follow reduced-motion preferences. Native input focus and DOM buttons are retained through snapshots.
